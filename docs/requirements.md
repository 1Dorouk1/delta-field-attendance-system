# DELTA Employee Field Attendance System

## Updated master requirements

**Status:** Authoritative MVP specification  
**Company:** DELTA – Public Accountants & Consultants  
**Timezone for display:** `Africa/Cairo`  
**Languages:** English and Arabic

This specification supersedes conflicting earlier requirements. The current MVP has no selfie, camera, image upload, image storage, or image verification functionality. No image storage service, SDK, API, or image-related cloud resource is to be installed, configured, or charged for in this MVP. A future paid version may add an optional verification module behind a separate interface and deployment boundary; that future module is not part of the MVP and must not affect attendance availability.

## 1. Product objective

Provide DELTA employees and authorized administrators with a secure, responsive web application for recording independent attendance Check-ins from any location. A record contains employee identity, a one-time GPS location capture, GPS accuracy, and a timestamp generated by the server. The application does not track employees continuously.

## 2. Business rules

- Employees may create unlimited Check-in records per day. Each accepted submission is a separate record.
- Check-out is not mandatory and there is no Check-out API requirement.
- Attendance is not restricted to an office, mission, geofence, or predefined destination.
- There is no live tracking, background location collection, movement history, or continuous GPS polling.
- A Check-in requires valid coordinates that meet the configured accuracy threshold. A selfie or any other image is never required.
- Duplicate requests caused by repeated taps or network retries must not create duplicate records. Use a client-generated idempotency key scoped to the employee and enforce it in the database/API.
- The browser's location acquisition timestamp is evidence metadata only. It never replaces the authoritative server timestamp.
- A successful submission is confirmed only after the database transaction commits.
- GPS signals can be inaccurate or spoofed; the interface must not claim GPS alone proves identity or prevents spoofing.

## 3. Approved technology

- Frontend: semantic HTML, CSS, vanilla JavaScript ES modules; responsive web app and optional PWA.
- Backend: Node.js and Express.js REST API.
- Persistence: PostgreSQL with Prisma ORM and migrations.
- Maps: Google Maps JavaScript API for historical attendance locations, subject to configured/restricted keys.
- Location: Browser Geolocation API, invoked only after an employee initiates Check-in.
- Authentication: secure cookie sessions, HttpOnly cookies, bcrypt password hashes, server-side authorization.
- No camera or MediaDevices API, image-related packages, object storage, image hosting, or image service credentials in the MVP.

Use the approved original DELTA logo at `frontend/assets/images/delta-logo.png` without modification. Brand colors: navy `#111D4A`, secondary navy `#1B2859`, turquoise `#55B8B2`, white `#FFFFFF`, background `#F5F7FA`. Use Cairo for Arabic and Inter for English. Support current Chrome, Safari, Edge, and Firefox on iPhone, Android, tablets, laptops, and desktops. The system remains usable in a browser without installation.

## 5. Languages

Provide complete English and Arabic interfaces, including navigation, forms, validation, errors, notifications, reports, and attendance details. Include a language switcher, Arabic RTL, English LTR, persisted user preference, and configurable default language. Keep strings in centralized translation dictionaries, not page components.

## 6. Roles and authorization

### Super Admin

Manage users, employees, departments, manager assignments, system settings, role permissions, audit logs, all attendance records, maps, and reports.

### HR / Admin

Manage employees and account status; view attendance and locations; manage departments when authorized; review submissions; and export authorized reports.

### Manager

View employees, attendance records, historical locations, and reports only within assigned departments or explicitly assigned organizational scope. Enforce this scope in backend authorization and database queries, never only in the UI. Changing IDs or query parameters must not expose other departments.

### Employee

Log in, register Check-ins, view only personal attendance history/details, update permitted profile fields, and change password. Employees must not access other employees' records.

## 7. Employee portal

Pages: Login, Employee Dashboard, Register Attendance, Attendance History, Attendance Details, Profile, Settings.

Login accepts Employee ID or email and password, supports Remember Me and Forgot Password, and uses the DELTA logo.

Dashboard displays employee name and ID, profile photo if already part of the employee directory, department, job title, current date, today's submission count, latest attendance record, and an enabled Check-in action whenever the authenticated employee is eligible. Existing records today must not disable another Check-in.

### Check-in workflow

1. Employee clicks **Check-in**.
2. Browser requests GPS permission.
3. System obtains the current coordinates and reported accuracy using the Browser Geolocation API.
4. System validates coordinate ranges and the configurable maximum accuracy (initial recommendation: 100 meters).
5. Employee reviews the location (coordinates, accuracy, and map/address when available) and may retry GPS acquisition.
6. Employee confirms Check-in.
7. Backend authenticates/authorizes the request, validates the payload, prevents an idempotent duplicate, and generates the authoritative server timestamp.
8. PostgreSQL stores the attendance record.
9. After commit, the UI displays successful registration and the server time.

No camera permission, selfie capture, image preview, image confirmation, image upload, or image validation is part of this flow. No image is required to register attendance.

### GPS requirements

Request location only after Check-in is initiated. Use a one-time location request, not watch/continuous updates. Production requires HTTPS. Explain denied permission and unavailable/disabled GPS in both languages; allow retry. Enforce configured accuracy and coordinate bounds. Do not trust client timestamps and do not claim coordinates are tamper-proof. Store latitude, longitude, reported accuracy, and optional acquisition timestamp; reverse-geocoded address is optional.

## 8. Attendance records and review

Every record represents exactly one Check-in and includes:

- ID, employee ID, department ID snapshot, attendance date, and server timestamp (UTC).
- Latitude, longitude, accuracy in meters, optional acquisition timestamp, and optional address.
- Submission idempotency key and creation timestamp.
- Review status (for example `pending_review`, `reviewed`, `flagged`, `rejected`) and reviewer metadata where applicable.

There is no checkout field, image field, photo relation, or verification state that depends on an image. GPS capture is evidence collection, not proof against all location spoofing. Any administrative correction/review must be audited and must preserve the original submitted evidence.

## 9. Administration, maps, and reporting

Admin pages: Dashboard, Employee Management, Department Management, Attendance Management, Attendance Map, Reports, User Management, Audit Logs, System Settings. Dashboard metrics distinguish total submissions from unique employees and show department statistics and trends.

Attendance tables include employee, department, date/time, GPS location, accuracy, and review status. Filters include date/range, employee, department, and review status. Authorized manual changes are audited.

Google Maps shows historical attendance markers only. Marker details include employee name/ID, department, date/time, accuracy, and map link. Support date/department/employee filters and clustering when needed. No map is continuously refreshed to track people. Manager map responses are scoped by backend queries to authorized departments.

Reports include daily, weekly, monthly submissions, employee history, department report, location report, and flagged/review report. Do not define a selfie verification report. Exports: XLSX, CSV, PDF. Managers can export only authorized records. Reports distinguish total submissions, unique employees, and submissions per employee.

## 10. Security, privacy, and operations

Implement bcrypt password hashing, secure HttpOnly cookies, CSRF protection, rate limiting, Helmet, input validation, authentication and role/department authorization, audit logging, secure environment variables, restricted CORS, database backups, and HTTPS. Do not expose sensitive employee details or attendance records through public endpoints. Define company-approved retention periods for attendance records and an administrative review/correction process. No image retention policy or image data processing exists in the MVP.

Use restricted Google Maps keys and appropriate production error monitoring. Do not claim integrations are operational until configured and verified.

## 11. Modular architecture and future paid extension

Keep domain boundaries clear: attendance, identity/access, employee/department administration, location, maps, reports, audit, and translations. Attendance creation depends on a small optional-evidence extension point/interface that is absent or a no-op in the MVP; the core Check-in contract and database schema must work without it. Any future paid selfie/private-storage capability must be a separately enabled module with its own authorization, private storage adapter, retention controls, migration, and tests. Do not add placeholder image tables, routes, packages, credentials, storage buckets, or running services now. The extension point must not impose an image dependency or image cost on the MVP.

## 14. Acceptance criteria

1. Employees can securely log in.
2. Employees can make multiple independent Check-ins per day without a daily cap.
3. Each Check-in requires valid GPS coordinates and configured accuracy, but no selfie or image.
4. Every accepted record has an authoritative server timestamp.
5. Check-out is not required; no live/background tracking exists.
6. Managers only receive authorized department data.
7. Arabic/English and RTL/LTR work throughout the app.
8. Google Maps displays historical records after configuration.
9. Reports can be exported within authorization scope.
10. Security/privacy requirements are implemented and verified.
11. Supported mobile and desktop interfaces work responsively.
12. PostgreSQL/Prisma, API, deployment, and operational documentation are complete.
13. MVP starts and operates without any image storage service, image-related dependency, or image cloud cost.
